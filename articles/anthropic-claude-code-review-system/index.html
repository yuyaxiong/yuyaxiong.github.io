ENGINEERING SYSTEMS · ANTHROPIC CASE STUDY

当 AI 写下大部分代码，
谁来保证它没有出错？

这不是一篇“用 AI 帮忙审代码”的工具介绍，而是一套关于注意力分配、验证证据、风险分级和组织责任的研发系统设计。

一段时间里，AI 编码工具被讨论最多的是：它能写多快、一次写多少、开发者如何写好 Prompt。随着 Agent 真正进入团队的日常交付，问题却变得不同：如果每个人都能同时启动多个 Agent，代码量快速扩张，谁有能力逐行阅读所有变更？如果代码出错，应该在哪个环节发现？最后又由谁承担结果？

Anthropic 在这篇工程实践文章里给出的答案，不是取消 Code Review，而是把它拆解为可以分别优化的多层系统。这套方法的边界也很明确：人力时间可以节约，但事故与回滚不能因此增加。

本文核心问题

从“所有代码都让人看一遍”，转向“不同风险应该由什么证据和什么角色来承担”。这不是审查强度下降，而是审查能力的重新配置。

01｜为什么传统 Code Review 遇到规模极限

在人手写代码的时代，编码、审查和知识传递主要以人的速度发生。人工逐行审查虽然昂贵，却天然受到代码产量的限制。Agent 改变了这一约束：代码生成速度大幅提高，人类阅读和理解代码的速度却不会同步增长。

原文重新拆分 Code Review 的两个职能：质量保障（上线前发现问题）和知识共享（让团队理解系统如何变化）。如果把两件事都交给“同事逐行看 Diff”，就会在产出扩张时同时成为瓶颈。

作者因此提出一个不同的问题：这次变化真正可能造成哪些失败？哪个检查最适合发现这些失败？有些错误交给编译器和测试，有些交给 AI Review，有些必须交给熟悉系统的人类。

这给研发管理的启示是：不要只优化人均代码产出，而应该优化从需求确认到可靠上线的完整系统吞吐，并把事故处理成本算进去。

02｜目标函数：节省人的时间，不是盲目减少审批

团队追踪的不是单一的“AI Review 覆盖率”，而是每个 PR 所需的人类注意力，包括人工批准数量的中位数与 P95、人工评论量，以及 PR 等待人工处理的时间。与之配套的保护指标则是回滚率和生产事故率。

理解 Anthropic 的优化目标

在事故率、回滚率不增加的约束下，尽可能减少每次可靠交付对人工关注的占用。降低审批分钟数却让线上修复工时暴涨，不是效率提升。

团队的目标是：在 Claude Code 的 CLI、桌面、Web 与移动应用仓库中，大多数 PR 最多只需一位人类参与；对于特定变更，这个人可以就是发起该变更的人。注意这是一个基于成熟自动化保障体系的目标，不是建议所有团队直接取消审查。

从经济学角度，可以把一次变更的期望成本拆为：审查成本 + 返工成本 + 事故的预期损失。前者容易在仪表板里观察，后两项可能发生在数天甚至数周之后，因此必须长期联动追踪。

03｜整套质量保障系统究竟如何运行

原文展示了从开发者本地，到 PR、合并队列、灰度发布和事故回滚的完整路径。可以将它归纳为六道主要控制层，以及底部的故障恢复体系。

第一层，要求 Agent 展示可运行的证据。比如让它执行单元测试和构建、对照 UI 截图、在模拟器或浏览器走完真实流程，而不是只接受一句“已经完成”。团队在 PR 提交前还会调用擅长找 Bug、简化 Diff、端到端检查的不同 skill。

第二层，每个 PR 都有自动 Code Review。AI 结合变更意图、仓库上下文和代码 Diff 判断：问题是否真正解决？实现是否适合架构？是否影响其他模块？多个 Agent 并行寻找问题，另一组 Agent 复核候选发现，再按严重度留下可执行的评论。团队曾观察到，有实质性审查评论的内部 PR 占比从 16% 提高到 54%；这表示审查发现更充分，不等同于“Bug 率变成 54%”。

第三、四层是强约束。安全与代码问题线程不能挂着不管，必须修复或明确说明关闭原因；CI 要运行格式、类型、跨平台测试、构建等校验。PR 模板要交代“怎么测试”和“如何撤销”。

第五、六层关注风险与集成。即使两个 PR 分别通过测试，合入同一个 main 仍可能互相冲突，因此合并队列要重新验证。新行为通常先在内部环境或灰度渠道使用，保持可关闭、可回滚。

最重要的一点是，作者并没有假设这六层能够发现所有错误。它通过快速发现与快速恢复来控制剩余风险。这就是为什么 Feature Flag、值班体系与事故复盘不只是发布后的附属设施，而是整个质量系统的一部分。

04｜CLAUDE.md、REVIEW.md 和审查 Agent 怎样分工

这套流程的效果，依赖 Agent 是否知道项目里的真实约束。原文强调两个不同目的的上下文文件：

CLAUDE.md｜项目约定

描述技术栈、编码风格、目标与非目标、目录约定和验证命令。应该保持简短，让更多详细信息通过链接或按需加载获得。

REVIEW.md｜失败模式

由代码负责人维护，明确什么问题最重要、哪些路径可以跳过、如何提供文件与行号证据，以及如何限制纯风格类噪声。

在这套设计中，Review Agent 不只是扫描语法错误。它需要理解 PR 的目的及变更的上下游影响。对 Bug 修复，还要判断补丁是否触及根因，而不只是遮蔽症状。

评论分级也很关键。原文会区分真正重要的问题、轻微建议和变更之前就存在的问题，避免把历史技术债错误归责给本次提交者。

另一个工程上的成熟做法是：如果 Reviewer 总在同类问题上重复提醒，就将约束前移到规则、Skill、Lint 或项目说明里。这样，新 Bug 尽可能在更靠前、更便宜的环节被挡住，而不是让人工或 Agent 永远重复讨论。

05｜低、中、高风险，为什么要采用不同审批策略

原文把人工审批从一个统一规定，改为依据变更风险动态分配。其逻辑不是“新人必须多审、资深可以随便合”，而是变更的影响决定风险等级。

LOW · 低风险0 人

文档、文案、内部功能、受开关保护的新增改动；前提是自动检查与安全审查全部通过。

MEDIUM · 中风险1 人

普通产品改动，以及缓存、自动更新、系统提示词等敏感逻辑。

HIGH · 高风险2 人

最关键的高风险代码，和被明确列为双人审批的特殊路径。

风险分类器判断变更等级；第二个分类器补充检查是否仍需要额外人工。受保护文件、CI 工作流等路径强制要求人类参与。较轻的审批机制只向可信任提交者开放；Agent 的“通过”不能冒充人工批准。

还有两个容易被忽略的细节：第一，审批只对某个明确的提交版本有效，如果发生系统无法确认的新提交，需要重新获得批准；第二，驱动 Agent 完成 PR 的人，依然被视为对代码负责的提交者，不能把责任转移给模型。

落地边界

风险分级的前提，是团队知道哪些业务资产最贵、哪些错误最难发现、哪些变更最难回滚。没有这些边界，就不应照搬“低风险零人工审批”。

06｜让 Code Review 持续变好：以线上事故做评测

一套 AI 审查系统会持续变化：模型升级、Prompt 改写、工具增减、仓库架构演进。怎样判断这些变化是在改善 Reviewer，而不是只让它输出更多评论？Anthropic 的方法是构建自己的真实事故评测集。

团队收集历史上引发事故的 PR、之后的修复与回滚，让熟悉代码的工程师确认缺陷与真实位置，再用它们每天检验 Reviewer 的识别能力。每次新增事故，都能成为新的回归题。

原文尤其重视误报成本。真实工程师看到一个不重要的建议，可能只需几秒钟忽略；编码 Agent 却很可能真的修改代码，于是产生下一次提交和下一轮审查。自动化使“无效建议”从阅读成本变成实际生产成本。

因此团队不仅统计有多少缺陷被发现，也会观察人工如何回应每条评论：确实修复、判为错误、认为行为是故意的，还是认为不值得更改；另外还会用已知正确的 PR 检查 Reviewer 是否提出会引入缺陷的建议。

07｜为什么 AI 审查必须收敛：50 多轮的教训

Agent 编码、Agent 审查听起来像一个可以无限自动优化的闭环，现实却可能出现反效果。原文提到，一次 CLI 的 PR 在一夜之间经过 50 多轮审查和修补，仍没有自然结束。

排查之后，团队发现重复标记的问题中约 59% 指向第一次审查时就存在的代码。新的审查往往不是真正找到“刚刚引入的新 Bug”，而是在更晚的轮次中继续挖出原本就存在的旧问题。对一部分高风险改动，这种深挖可能值得；但对所有 PR 都这样做，吞吐量会被耗尽。

改善措施包括：常规场景下三轮之后暂停并重新思考实现方式；几轮后只重新审查新 Diff；指出缺陷类别以便批量修复；不要重复发布已经提醒过的问题。团队还会追踪“通过所需审查轮数”，而不只是发现真实 Bug 的召回率。

一个重要的 Agent 设计原则

Agent 工作流必须有停止条件、增量边界与成本预算。否则把两个能力不错的 Agent 串在一起，也不一定会得到更好的系统。

08｜人类还需要做什么？知识如何流动？

作者没有宣称人类退出软件交付。他们把人的主要价值放在更难被形式化的判断：是否应该做、需求范围是否合理、风险代码是否值得上线、架构是否会被别人照搬，以及自动化验证证据究竟覆盖了什么、遗漏了什么。

尤其是“读证据”这一点：测试通过有时只意味着测试没覆盖出错路径；一个审查结论正确，也可能因为上下文不足而看不到业务级缺陷。负责上线的人必须有能力提出“哪些情况没有被检查到”。

对于 Code Review 的第二项历史功能——团队共享代码理解——作者提供了一种新实践：不要求所有人持续阅读全部 Diff；当某个人需要改动一个模块时，再让 Claude 根据最新代码解释那个局部，必要时生成可视化材料，帮助迅速建立理解。

这并不意味着共享架构知识不重要，只是传播方式从“通过阅读所有日常代码变更来吸收”逐渐转向“针对当前任务，按需获取系统上下文”。团队开放的协作频道也是促进旁观学习与交叉反馈的重要机制。

代码可以交给 Agent 实现，
但“该不该做、做到什么程度、出了问题谁负责”仍必须有清楚的答案。

原文还强调一个团队约定：谁推动变更落地，通常就负责其后续修复。这个约定建立在小 PR、可逆发布、快速遥测和明确风险范围上，并不主张事故后的追责羞辱；事故复盘应该检查系统哪一道关卡本来可以避免问题。

09｜开发成本下降后，组织应该更愿意推翻错误方向

过去，一个功能实现消耗了大量工程师时间，团队很容易产生沉没成本：虽然方向已经有疑问，还是希望先合并再说。Agent 让试错更便宜，也意味着否决错误方向的心理成本应当同步下降。

作者观察到，方向不同的意见最好在开放讨论中尽早提出，而不是等 PR 完工再用阻断评论表达。开发者可以关闭、缩小或者重新规划某个已经写好的 PR，而不用把它看成不可承受的浪费。

这实际上提出了一个对研发组织更严肃的要求：既然实现已经便宜，管理者就应把更多注意力用在问题定义、方案比较和投资决策上。写出来的代码越多，越需要有纪律地放弃不值得合入的部分。

10｜团队可以怎样分阶段复制这套方法

最稳妥的路径不是直接上线全自动合并，而是先让每个变更都有可验证证据，再逐步根据实测风险放宽审批。

  1. 先建立最小检查面

    让 Agent 能运行构建、测试、格式检查；在项目说明中列出可执行命令与禁区。

  2. 每个 PR 引入 AI Review 与安全检查

    补充 PR 模板：Testing、Risk、How to revert；所有发现都要处理或写明理由。

  3. 制定基于变更的风险等级

    结合 CODEOWNERS、分支保护、敏感文件清单，对支付、权限、发布及架构改动保留人工决策。

  4. 建立合并与上线保护

    使用合并队列、Feature Flag、内部测试、灰度发布与快速回滚，不依赖“所有 Bug 必须在上线前发现”的幻想。

  5. 把事故沉淀成评测闭环

    量化审查缺陷召回、误报、收敛轮数、人工耗时、回滚率与事故率；实证有效后再扩大低风险自动化范围。

对以 AI 应用和后端服务为主的团队，还可以把系统 Prompt、检索路由、工具权限、模型版本、发布配置视作与核心代码同等重要的可审查变更。它们有时只有几行，却可能影响上万次真实请求。

并非所有问题都能靠 Lint 与单测捕获。对于 AI 系统，应该配套场景级离线评测、回归问题集、灰度反馈和业务结果监测，避免技术层面“测试通过”掩盖产品层面的错误。

11｜对原文的延伸判断与尚未解决的问题

以上是文章公开描述的主要设计逻辑。下面三点属于本文的延伸判断，而非 Anthropic 给出的结论。

共同盲区

编码与审查 Agent 可能在相同模型偏差上达成一致。多 Agent 复核能够降低部分错误，却不能替代确定性测试和真实环境验证。

监控闭环尚未完全自动化

原文坦言还没有根据回滚或事故指标自动收紧审批的熔断机制。随着零人合并比例上升，这会是重要的下一步控制能力。

代码正确不等于需求正确

一项功能即使通过所有技术测试，也可能没有用户价值，或与业务策略相冲突。产品判断需要另外的实验体系。

质量目标应当包含长期维护

如果只统计当期 PR 数与短期回滚率，可能低估未来架构复杂度、认知债务和运维负担。

所以我从这篇文章带走的核心结论是：AI Native 研发的优势，最终不取决于“谁写出更多代码”，而取决于谁能在明确责任、可观测风险与可恢复故障的条件下，更快获得可靠的业务结果。
